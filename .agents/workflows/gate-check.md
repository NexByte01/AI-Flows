# 阶段门禁检查

## 目标

检查当前项目是否满足进入下一阶段的标准。快速定位阻塞项，避免在未达标时推进。

## 适用场景

- 当前阶段的任务基本完成，准备推进到下一阶段。
- 需要快速了解离阶段目标还差什么。
- 阶段复盘时，确认哪些标准已达标、哪些未达标。

## 默认前提

- 已读取根级 `AGENTS.md`、`MEMORY.md`、`projects/registry.yml`。
- 已确认当前主项目和所处阶段。

## 阶段模型

项目可自定义阶段，常见模型：

| 阶段 | 说明 |
|---|---|
| Discovery | 需求调研、可行性分析 |
| Design | 架构设计、技术选型 |
| Development | 核心功能实现 |
| Validation | 测试、验证、质量达标 |
| Launch | 部署、发布、上线 |
| Operations | 运维、迭代、优化 |

阶段定义可在项目 `MEMORY.md` 中自定义。如项目有专门的阶段文档（如 `docs/phases/`），以该文档为准。

## 标准步骤

1. **确认当前阶段**：从 `projects/<slug>/MEMORY.md` 读取当前阶段和目标阶段。

2. **提取通过标准**：从阶段文档或项目 `MEMORY.md` 中提取门禁标准条目。若无显式标准，根据阶段类型推断通用标准。

3. **逐条检查**：
   - ✅ 已满足：有明确证据。
   - ⚠️ 部分满足：有产物但不完整或未验证。
   - ❌ 未满足：缺少必要产物或状态。

4. **生成门禁报告**：

```text
当前项目：<slug>
当前阶段：<current_stage>
目标阶段：<target_stage>
检查时间：<timestamp>

门禁检查结果：
✅ [1/N] 门禁描述 — 证据：...
⚠️ [2/N] 门禁描述 — 现状：... / 差距：...
❌ [3/N] 门禁描述 — 缺失：...

总评：X/N 通过，Y 部分通过，Z 未通过
建议：<可推进 / 需先完成阻塞项>
```

5. **后续动作**：
   - 全部 ✅：建议更新项目 `MEMORY.md` 的阶段状态。
   - 存在 ❌：将阻塞项写入 `memory/tasks.md` 并标注为高优先级。
   - 在当天日志中记录本次检查结果。
   - 运行 `/closeout` 的最小收尾检查。

## 通用门禁参考

若项目未自定义门禁标准，可参考以下通用检查项：

### Development → Validation
- [ ] 核心功能可运行（有演示或截图）
- [ ] 关键路径有测试覆盖
- [ ] `docs/ARCHITECTURE.md` 已更新
- [ ] 无 blocker 级技术债

### Validation → Launch
- [ ] 所有测试通过
- [ ] 性能达到可接受水平
- [ ] 安全检查完成（API Key、权限）
- [ ] 部署文档或脚本就绪
- [ ] 用户文档/说明已编写

## 验收标准

- 门禁报告覆盖了所有定义的通过标准。
- 每个标准有明确的 ✅/⚠️/❌ 判定和证据。
- 阻塞项已同步到项目任务列表。
- 不跳过任何门禁标准。
