# 项目状态一览

> 用于回答以下类型的问题：
> - “分析当前项目进度”
> - “现在做到哪一步了”
> - “还有哪些风险 / 缺口”
> - “接下来应该做什么”

## 执行原则

- 先看**本地真实状态**，再下结论，不凭记忆概括
- 优先关注：
  - 当前分支与未提交变更
  - 远端是否已配置、是否可访问
  - `.github/workflows/` 是否与当前仓库目标一致
  - `memory/` 是否记录了本次阶段性工作
  - `site/` 与 `media-platform/` 的改动范围
- 涉及 Git 时：
  - 可以读取状态
  - 不自动执行提交、切分、推送、合并
- 如需联网信息，优先用已接入的 GitHub 连接器；没有可用工具时只基于本地状态说明

## 建议检查顺序

### 1. 本地仓库状态

查看以下信息：

```bash
git branch --show-current
git status --short
git log --oneline -5
```

重点回答：
- 当前所在分支是什么
- 是否存在未提交改动
- 最近在推进哪一类工作

### 2. 远端与协作状态

```bash
git remote -v
```

重点回答：
- 当前远端是否已配置
- 当前仓库是走 HTTPS 还是 SSH
- 如 GitHub 工具可用，补充说明仓库权限、未合并 PR 或开放 Issue 情况

### 3. 代码与内容完成度

优先检查：
- `.github/workflows/`
- `.agents/skills/`
- `.agents/workflows/`
- `site/`
- `media-platform/`
- `memory/`

重点回答：
- 仓库规则、记忆资产和自动化是否闭环
- 哪个子目录改动最多，当前工作重心在哪
- 是否存在明显占位内容、过期流程或未同步文档

### 4. 工程健康度

优先检查：

```bash
python -m py_compile media-platform/backend/*.py
```

重点回答：
- Python 后端是否存在明显语法问题
- GitHub Actions 或 YAML 是否需要静态复查
- 是否有阻塞协作或提交流程的问题

### 5. 远程协作状态（如工具可用）

如当前会话可使用 GitHub 工具，可补充检查：

- 未合并 PR
- 未关闭 Issue
- 当前仓库权限和默认分支
- 与本地工作流假设是否一致

如工具不可用，明确说明“以下结论仅基于本地仓库”。

## 输出格式

按以下结构输出，避免只罗列命令结果：

### 1. 当前阶段判断

用 1 段话说明项目目前处于什么阶段，例如：
- 设计 / 骨架期
- 前台已成型，运营能力未闭环
- 可发布，但仍有上线风险
- 已上线，进入优化与迭代阶段

### 2. 状态摘要

用简洁表格或短列表概括：

| 项目 | 状态 |
|------|------|
| 当前分支 | `main` / `feature/*` / `fix/*` / `docs/*` / `chore/*` |
| 未提交改动 | X 个文件 |
| 最近工作重点 | 例如“工作流整理 / 站点页面 / 多媒体后端” |
| 远端状态 | 已配置 / 未配置 |
| 记忆文件 | 已更新 / 待更新 |
| 重点目录 | `site/` / `media-platform/` / `.github/workflows/` / `.agents/` |
| 基础校验 | 通过 / 失败 / 未检查 |

### 3. 主要问题

按严重度列出：
- 当前阻塞项
- 非阻塞但重要的风险
- 明显的产品 / 工程缺口

### 4. 下一步建议

给出按优先级排序的 3–5 项建议，要求：
- 可执行
- 按依赖顺序排列
- 尽量分清“先修发布质量”还是“再扩功能”

## 额外要求

- 如果用户问的是“项目进度”，回答重点应是**阶段、风险、下一步**
- 如果用户问的是“仓库状态”，回答重点应是**分支、未提交变更、最近提交**
- 如果用户问的是“能不能上线”，回答重点应是**工作流、Pages 部署、子项目说明、仓库配置是否齐全**
- 发现工作区脏状态时，要区分：
  - 用户已有未提交工作
  - 当前会话新增改动
  - 不要把两者混为一谈
