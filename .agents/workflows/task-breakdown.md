# 任务拆解工作流

## 目标

从用户需求或项目文档中拆解出可执行的原子任务，写入项目级 `memory/tasks.md`。解决"方案写得好但不知道第一步做什么"的问题。

## 适用场景

- 项目进入新阶段，需要把文档或需求转化为可执行任务。
- 用户提出一个较大的功能需求，需要拆分为多个独立可验证的步骤。
- 当前 `tasks.md` 中的待办项过于笼统（如"建立 MVP"），需要细化。

## 默认前提

- 已读取根级 `AGENTS.md`、`MEMORY.md`、`projects/registry.yml`。
- 已确认当前主项目。

## 标准步骤

1. **确认拆解来源**：
   - 从项目文档或阶段方案中提取"关键动作"。
   - 或从用户当前需求中提取工作项。

2. **确认当前状态**：
   - 读取项目 `MEMORY.md` 和 `memory/tasks.md`，确认已完成项。
   - 避免拆出已完成的任务。

3. **拆解规则**：
   - 每个任务必须是**原子可验证**的：做完后能通过一个明确的检查确认完成。
   - 每个任务包含：
     - **描述**：一句话说明做什么。
     - **产出物**：完成后应存在的文件或状态。
     - **依赖**：必须先完成哪些任务。
     - **规模**：S（< 30min）/ M（30min–2h）/ L（2h+）。
   - 按依赖关系排序，无依赖的任务排在最前。
   - 单次拆解不超过 10 个任务。超出则只拆当前最紧急的部分。
   - 为减少 Token 消耗，`tasks.md` 的"下一步"只保留当前 5-10 个高优先级任务；旧完成项应归档到当天日志或阶段记录，不长期堆积。

4. **写入任务**：
   - 更新 `projects/<slug>/memory/tasks.md`。
   - 新任务放在"下一步"区域。
   - 保留已有的"已完成"和"暂不做"列表。

5. **更新状态**：
   - 更新项目 `MEMORY.md` 的当前阶段描述（如果阶段有变化）。
   - 在当天日志中记录本次拆解。
   - 如果任务拆解涉及架构变化，执行 `/closeout` 的架构与日志检查。

## Token 控制

- 拆解前只读取相关文档，不默认读取全部项目文件。
- 不把长方案全文复制进 `tasks.md`，只写可执行任务和产出物。
- 已完成任务超过当前恢复所需时，应移动到 `memory/YYYY-MM-DD.md` 或阶段归档。

## 输出格式

```markdown
## 下一步

- [ ] [S] 任务描述 → 产出物：`path/to/file`
- [ ] [M] 任务描述（依赖：上一任务） → 产出物：`path/to/file`
- [ ] [L] 任务描述（依赖：前两个任务） → 产出物：可运行的 CLI 命令
```

## 验收标准

- 每个任务可独立完成和验证。
- 无循环依赖。
- 第一个任务可以立即启动，不需要额外前置条件。
- 任务列表覆盖了来源文档或用户需求的完整范围。
