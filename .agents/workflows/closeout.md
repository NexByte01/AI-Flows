# 收尾自动化工作流

## 目标

在每次较大任务完成后，用最小必要上下文完成收尾：验证结果、任务状态、每日记录、架构文档和后续动作。目标是提高持续迭代效率，同时避免无边界读取导致 Token 浪费。

## 适用场景

- 完成代码实现、架构变更或重大功能交付。
- 完成文档重构或规则变更。
- 用户指出遗漏了任务、日志或架构更新。
- 准备提交前，需要确认本轮工作是否真的闭环。

## Token 预算原则

默认只读取最小必要文件：

1. 根级 `AGENTS.md`
2. 当前项目 `MEMORY.md`
3. 当前项目 `memory/tasks.md`
4. 本次改动相关文件
5. 当天 `memory/YYYY-MM-DD.md`，仅用于追加或确认本日记录

禁止默认全量读取：

- 历史每日记录。
- 大型输出目录。
- 完整架构文档全文，除非本轮触发架构变更。
- 第三方长文档或通用参考资料，除非当前问题需要引用。

读取升级规则：

- 需要确认架构一致性时，读取 `docs/ARCHITECTURE.md` 的相关章节，而不是全文重写。
- 需要追溯历史原因时，优先搜索文件名和关键词，再读取命中的 1-2 个文件。

## 标准步骤

1. **确认工作类型**
   - 标记本轮是否包含：代码变更、架构变更、文档治理、任务拆解。
   - 若只回答问题且无文件变更，通常不需要完整收尾。

2. **验证**
   - 代码变更：运行项目约定的最小验证，例如 `pnpm typecheck`、`pnpm test`、`pnpm build`。
   - 文档/记忆变更：检查目标文件存在、关键标题/关键词存在。

3. **更新任务**
   - 当前项目任务只写入 `projects/<slug>/memory/tasks.md`。
   - 下一步必须保持短、可验证、按优先级排序。
   - 已完成区只保留近期高价值完成项；旧流水账应移入每日记录或阶段归档。

4. **更新每日记录**
   - 只要涉及架构、核心模块、API 接口或关键能力的变更，必须更新 `memory/YYYY-MM-DD.md`。
   - 根级日志只记录跨项目影响，不复制项目日志全文。

5. **检查架构**
   - 触发条件：新增核心模块、外部服务接入、数据模型变更、API 路由变更或关键运行时能力变化。
   - 若触发，更新 `docs/ARCHITECTURE.md` 的相关章节、`last_verified` 和变更日志。
   - 不重写整篇架构文档。

6. **输出收尾摘要**
   - 只列本轮实际改动、验证结果、未完成风险和下一步。
   - 不重复粘贴长日志、长任务列表或整段架构说明。

## 强制检查矩阵

| 变更类型 | 必须检查 |
|---|---|
| 新核心模块 / 服务 | `ARCHITECTURE.md`、项目日志、tasks |
| 新外部 API / 第三方集成 | `ARCHITECTURE.md`、`.env.example`、项目日志 |
| 新 CLI 命令 / API 路由 | `ARCHITECTURE.md`、测试、项目日志 |
| 数据模型 / Schema 变更 | `ARCHITECTURE.md`、迁移文件、项目日志 |
| 只改文档规则 | 目标文档、根级日志或项目日志 |
| 依赖升级 | `package.json`、锁文件、测试 |

## 验收标准

- 用户不用提醒每日记录、架构文档或任务状态。
- 每次较大任务都有清楚的验证结果。
- 不为了恢复上下文读取大量历史文件。
- 下一步任务保持可执行，不被已完成流水账淹没。
- 所有架构升级都有 `ARCHITECTURE.md` 变更日志。
